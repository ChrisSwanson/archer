# Known failures: root cause and remediation

Keep the application in a known, error-free state. Every failure seen in any run (CI, `npm run
pr-check`, a focused test, a manual check) is investigated to its root cause and remediated, whether
or not the current work caused it. A test is never skipped, loosened or deleted to make it pass
unless the investigation shows the test itself is wrong; that reasoning is recorded here.

One row per failure, added before its fix is pushed. Ids continue from the earlier record (O1–O274,
kept from development before the public release and not published; code comments and CHANGELOG
entries that cite an O-number refer to it), so new rows start at **O275**. Link the row's issue or PR where there is one.

Status: open → investigating → fixed (commit) / environment (what the host needs) / accepted (with reason).

| O275 | `diagram-canvas.render` "keeps reporting selection while an error banner is showing" fails on @xyflow/react 12.12.1. Root cause: xyflow #6097 stopped writing its internal `selected` flags in a controlled flow, so `onSelectionChange` no longer fires on a click. The page never listened to that prop, and the drawing under a read-error banner gets no click handlers on purpose (ADR 0010): the test asserted the opposite of the design and passed only through xyflow's side effect. The test was wrong. | Dependabot #12, CI and locally, every run | fixed: prop removed; the test asserts the drawing renders and a click reports nothing (mutation-checked) |
| O276 | Eight UI component tests fail on jsdom 31 (five on 27–30): accessible names such as "Files2 active" for "Files 2 active", plus `translate(60px, 90px)`, a zoom of 0.923077 and a computed `font-weight` of 400. Root cause: jsdom 27 derives name spacing from `display`, and Vitest gives jsdom none of the page's CSS, so flex children read as inline. Chromium with the built CSS gives exactly the names the tests expect, so the app is right. jsdom 31 also serializes CSSOM as browsers do, which three tests do not expect. A global `css: true` fixes the names but breaks twelve layout tests that assume no CSS. The tests: names in `disclosure-arrows`, `expand-menu`, `comments-loop` and `walkthrough-panel` (two); serialization in `canvas-authoring`, `canvas-fit` and `note-legend-focus`. | Dependabot #16, CI and locally | accepted: held at jsdom 26.1.0 (Dependabot ignores ≥27). The hold lifts once (1) those component tests load their own stylesheets (`tests/stylesheet.ts`; `WalkthroughPanel` must also import `walkthroughs.css` itself), (2) the three serialization assertions compare values rather than spellings, and (3) the contributor Node floor rises to jsdom 31's `^22.22.2 \|\| ^24.15.0 \|\| >=26` |
| O277 | `recovery.e2e` "an agent correction after offline restart…" fails on Playwright 1.65 with an unexpected `GET api/events` `net::ERR_ABORTED` (status 200) in the reload phase. Root cause: the test reloads while the event stream reopened after recovery is still open, and a reload always aborts an open stream. Playwright 1.65's Chromium reports that as a failed request and 1.63's did not. The app cannot avoid it. | Dependabot #12, CI and locally, 6/6 (1.65.0), 4/4 (1.65.1); passes 4/4 on 1.63 | fixed: the noise filter exempts at most one such stream, so a second (a leaked stream) still fails |

| O279 | `filter-sections.e2e` "filter sections stay bounded and keyboard-operable" (desktop, phone, short phone) fails on Playwright 1.65.1: `backgroundRepeat` is `"no-repeat"`, not `"no-repeat, no-repeat"`. | O280 | `sequence-block-app` "closing a newly saved participant / message discussion focuses its new SVG pin" fails with `expected null not to be null` at the pin lookup. Root cause (inferred from the failing line, not reproduced): the test waits for the comment's text, then looks up the thread's pin synchronously, assuming both land in the same render; under load the pin can come a render later. | O281 | `web-shell` "stays on the reader's tab when the agent's view is live-reloaded, and publishes their selection again" fails with two selection POSTs where one is expected. It was seen once, in a full `pr-check`, and passed 5/5 alone and 15/15 under `test:repeat --load 8`. Root cause (inferred, not reproduced): the test waited only `setTimeout(0)` after the click before clearing the fetch mock, while the selection sender's throttle window (`SELECTION_SEND_INTERVAL_MS`, 150 ms) was still open. On a slow run, a trailing send from the click lands after the clear, beside the reload's re-publish.
